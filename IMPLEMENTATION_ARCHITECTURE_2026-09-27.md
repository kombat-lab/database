# Результат архитектурного рефакторинга — 27 сентября 2026

Реализованы исправления и изменения структуры по `ARCHITECTURE_AUDIT_2026-09-27.md`. Исходная точка — `83cafd236518eff78a97dffdb219f167847d6e6e`. Аудит оставлен как исторический документ; текущие результаты и ограничения зафиксированы здесь.

## Исправленные сценарии

| Проблема аудита | Исправление и проверка |
| --- | --- |
| Удаление изменённого свитка из старого черновика | Отдельный снимок опубликованных ссылок проверяется при удалении, даже если в черновике уже выбран другой свиток. Старые черновики без снимка требуют переоткрытия. |
| Повтор кнопки дропа инвертирует результат | Явное желаемое состояние `set_drop_enabled`; повтор команды сохраняет результат и не увеличивает ревизию при отсутствии изменений. |
| Сбой доставки после UPDATE оставляет ввод активным | Запись каталога и следующий шаг долговечного FSM фиксируются одной транзакцией; отправка Telegram происходит после неё. Проверены ошибки сохранения FSM, доставки и повтор после открытия новой SQLite connection. |
| Изучение доступно без требования изучения | Проверка в доменной команде и административном UI; противоречивые старые отметки не присоединяются молча к новому свитку. |
| Точное совпадение теряется после LIMIT | SQL ранжирует точное совпадение и префикс до ограничения; inline имеет общий порядок и полноценную пагинацию. |
| Личное состояние используется на общей кнопке | Групповая карточка предлагает явные персональные действия изучения/снятия; личный чат показывает состояние пользователя. |
| Карта мира теряет тему и повторяет неоднозначную отправку | Общая политика доставки сохраняет тему и не делает повтор после неоднозначного сетевого сбоя. |

Дополнительное независимое ревью обнаружило два сценария публикации экранов: потерю доступного шага при ошибке показа совпадающих предметов и несоответствие видимого выбора дропа сохранённому FSM при ошибке записи. Привязка нового экрана, выбор и следующий шаг теперь фиксируются одним коротким сохранением после доставки; новые кнопки не принимаются, если это сохранение не завершилось. Проверены ошибка доставки, сбой после частичной записи выбора и сбой после записи нового токена с повторным открытием файловой SQLite. Тот же механизм используется для шагов создания и приглашения к изменению поля. Соседние проверки выявили и закрыли удаление другого ингредиента повтором старого индекса и применение следующего числового ответа к прежнему полю моба. Удаление материала адресует ID ресурса; новый payload и шаг публикуются вместе. До доставки сохраняется отметка незавершённого перехода, которая блокирует неоднозначный свободный ввод при сбое доставки/фиксации и исчезает после успешного подтверждения экрана.

## Структура и контракты

- `app.py` собирает приложение; `bot.py` запускает его. Независимые экземпляры имеют свои Dispatcher, базу, права, роутеры и фоновые задачи. Проверены два одновременно созданных приложения с разными базами и администраторами.
- `public_catalog.py` отвечает за публичные обработчики, `public_presentation.py` — за представление с явным `PublicContext`. Административные фабрики получают изолированный `RuntimeScope`. Совместимые старые адаптеры не перенастраивают глобальные зависимости production-приложения.
- `storage/sqlite.py` управляет соединением, отменой и транзакциями; `storage/schema.py` — миграциями; отдельные репозитории — сущностями, черновиками, рецептами, поиском и командами. `Database` сохраняет явный типизированный фасад и общий транзакционный контекст.
- SQL-строки декодируются из ограниченного `SqlValue` проверяемыми функциями. Административные данные формы проверяются при чтении; динамические variadic-команды заменены конкретными сигнатурами. `Any` ограничен интеграцией с aiogram/asyncio и протоколом FSM; перед использованием данных доменными командами выполняются проверки. В SQL, публичном каталоге и новых административных командах нет явных `Any`, `cast` или подавлений `type: ignore`.
- Доменные записи проверяют идентификаторы, в том числе запрещают `True` вместо ID 1; типы, слоты, редкости, количества, emoji и связи проверяются независимо от Telegram.
- Ресурсы, карты и встроенные материалы имеют общую проверку нормализованной идентичности. Админка предлагает существующую запись либо явно подтверждённый вариант. Повтор принятой команды распознаётся по сохранённому идентификатору и отпечатку запроса.

## Долговечность и эксплуатация

Все многошаговые формы используют `SQLiteFSMStorage`. Состояния имеют срок жизни, ограничение размера JSON и проверку структуры; чтение пустого контекста не создаёт запись. Истёкшие технические сессии удаляются небольшими порциями. Блокировки учитывают активных участников и ожидающих, освобождаются после последнего участника и корректно обрабатывают отмену.

Принятые Telegram updates завершаются до закрытия FSM. Фоновая аналитика завершается до закрытия SQLite и HTTP-сессии. Проверка использует настоящий lifecycle Dispatcher, включая `emit_shutdown`, а не только заменённую функцию polling.

`catalog_changes` атомарно сохраняет автора, идентификатор операции, источник и before/after. Ревизия каталога обновляется в той же транзакции. SQL-импорты должны использовать подключение приложения с зарегистрированными функциями журнала. Обычный SQLite read-only доступ подходит для анализа и backup.

История аналитики, журнал команд и завершённые черновики автоматически не удаляются. `python -m maintenance --database game.db` только показывает объём старых данных в read-only режиме. Автоматическая проверка безопасности отклонила первоначальное фоновое удаление существующей истории; реализация заменена предварительным подсчётом. На текущем снимке предварительный расчёт нашёл 0 завершённых черновиков старше 90 дней и 0 событий старше 365 дней.

## Производительность

Для синтетической inline-страницы из 50 простых ресурсов число SQL-запросов чтения через API уменьшено **со 154 до 6**. Служебные BEGIN/COMMIT в это число не входят. Повтор этой страницы при актуальном кэше выполняет **1** SQL-запрос ревизии. Это измерение обращений к данным, не обещание ускорения сетевой задержки в такое же число раз.

`catalog_reads.py` загружает ограниченный пакет связанных записей в согласованной read-транзакции; рендеринг выполняется после её завершения. `BEGIN DEFERRED` не резервирует блокировку писателя, что проверено отдельным подключением. Кэш ограничен 8 MiB сериализованного содержимого, 128 страницами и TTL 60 секунд; фактическая память объектов Python может быть больше веса сериализации. Ревизия включает связанные записи; проверены инвалидирование и завершение старого рендера после нового. Устаревшие inline-запросы отменяются независимо от аналитики.

Страница статистики выбирает пользователей до агрегации событий. `database.metrics` предоставляет количество, суммарное и максимальное время SQL. Каталог и аналитика пока используют общее соединение: доказательств необходимости пула или отдельной службы на текущем объёме нет. Архитектура рассчитана на один polling-процесс на токен и базу.

## Проверки и границы результата

Строгий mypy проверяет **59 модулей приложения**; Ruff и `git diff --check` проходят. Полный финальный прогон: **297 тестов прошли** на Python 3.12.14 (Windows), время 102.234 с. Проверки не используют рабочий Telegram API.

Тесты моделируют сбои Telegram, сохранения, отмену, конфликт редактирования и перезапуск через файловую SQLite. Рабочий бот с настоящим Telegram API не запускался; нагрузочная проверка внешнего сервиса не проводилась. Исправлены подтверждённые сценарии и архитектурные ограничения аудита, но наличие зелёных проверок не означает отсутствия любых возможных ошибок.
