# Fog Database Bot

Telegram-бот-справочник по мобам, ресурсам, снаряжению, картам и рецептам. Данные хранятся в SQLite. Администраторы редактируют каталог через `/kombat`; `/stats` показывает статистику только в личном чате.

## Запуск

Требуется Python 3.12. Запускайте один экземпляр polling-процесса на токен и базу. Настройки читаются один раз при запуске. Относительный DATABASE_PATH разрешается от корня проекта; явный абсолютный путь предпочтителен.

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:BOT_TOKEN = "YOUR_TELEGRAM_BOT_TOKEN"
$env:ADMIN_ID = "123456789,987654321"
$env:DATABASE_PATH = "E:\fog_database\game.db"
python bot.py
```

Linux/macOS:

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
export BOT_TOKEN='YOUR_TELEGRAM_BOT_TOKEN'
export ADMIN_ID='123456789,987654321'
export DATABASE_PATH='/srv/fog_database/game.db'
python bot.py
```

`.env.example` — шаблон переменных для среды запуска. Приложение **не загружает `.env` автоматически**. В сервисе задайте переменные окружения средствами менеджера процессов.

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | Токен Telegram Bot API, обязателен при запуске. |
| `ADMIN_ID` | Telegram user ID администраторов, разделённые запятыми; не username. Без ID административные функции закрыты. |
| `DATABASE_PATH` | Путь к SQLite; по умолчанию `game.db` в каталоге приложения. Отсутствующий файл останавливает запуск. |
| `ALLOW_EMPTY_DATABASE` | `true` явно разрешает создание новой пустой базы; по умолчанию `false`. Для существующей рабочей базы включать не нужно. |
| `FSM_TTL_DAYS` | Срок хранения незавершённых диалогов без обновлений, от 1 до 365 дней; по умолчанию 30. |
| `UPDATE_CONCURRENCY` | Максимум параллельно принятых обновлений, от 1 до 256; по умолчанию 64. |

Для первого запуска без готовой базы явно задайте `ALLOW_EMPTY_DATABASE=true`; каталог новой базы изначально пуст. При обычном запуске этот параметр оставьте выключенным, чтобы опечатка в пути не создала пустой каталог. Для инлайн-поиска включите inline mode у BotFather. Для событий выбора инлайн-результата отдельно включите inline feedback. Карточки используют Rich Messages; обычные сообщения служат fallback там, где это поддержано обработчиком.

Остановка через Ctrl+C/SIGTERM прекращает polling и ожидает принятые обработчики и фоновую аналитику до закрытия базы и HTTP-сессии. После grace period задачи отменяются, но завершение SQL/rollback всё равно дожидается окончания. Менеджер процессов должен дать время на это завершение; принудительное убийство процесса его обходит. При следующем запуске накопленные Telegram updates сохраняются.

## Резервные копии и восстановление

База работает в WAL-режиме. Простое копирование одного `game.db` у работающего процесса может пропустить данные из `game.db-wal`. Используйте SQLite backup API: оно создаёт согласованный снимок, включая уже зафиксированные WAL-транзакции.

Задайте отдельный каталог на другом диске или в защищённом хранилище. Не размещайте рабочие резервные копии внутри репозитория.

Windows PowerShell:

```powershell
$env:BACKUP_DIR = "E:\fog_database-recovery"
python -c "import os, sqlite3; from pathlib import Path; from datetime import datetime, timezone; p=Path(os.environ.get('DATABASE_PATH', 'game.db')).resolve(); root=Path(os.environ['BACKUP_DIR']).expanduser().resolve(); root.mkdir(parents=True, exist_ok=True); out=root / ('game-' + datetime.now(timezone.utc).strftime('%Y%m%d-%H%M%S-%f') + '.db'); src=sqlite3.connect(p.as_uri() + '?mode=ro', uri=True); dst=sqlite3.connect(out); src.backup(dst); print(out, dst.execute('PRAGMA quick_check').fetchone()[0]); dst.close(); src.close()"
```

Linux/macOS:

```sh
export BACKUP_DIR='/srv/backups/fog_database'
python -c "import os, sqlite3; from pathlib import Path; from datetime import datetime, timezone; p=Path(os.environ.get('DATABASE_PATH', 'game.db')).resolve(); root=Path(os.environ['BACKUP_DIR']).expanduser().resolve(); root.mkdir(parents=True, exist_ok=True); out=root / ('game-' + datetime.now(timezone.utc).strftime('%Y%m%d-%H%M%S-%f') + '.db'); src=sqlite3.connect(p.as_uri() + '?mode=ro', uri=True); dst=sqlite3.connect(out); src.backup(dst); print(out, dst.execute('PRAGMA quick_check').fetchone()[0]); dst.close(); src.close()"
```

Команда должна вывести путь новой копии и `ok`. База и копии содержат персональные данные и не должны публиковаться или попадать в Git. Ограничьте доступ к каталогу резервных копий средствами операционной системы и настройте отдельную политику хранения.

Для восстановления:

1. Полностью остановите все процессы, использующие эту базу.
2. Сохраните текущее состояние отдельной копией перед заменой. Если остались `game.db-wal`/`game.db-shm`, сохраняйте их вместе с соответствующим старым `game.db`.
3. Проверьте выбранную резервную копию через `sqlite3` и `PRAGMA quick_check` (результат `ok`).
4. Переместите старую базу и её sidecar-файлы в отдельную папку; скопируйте выбранный снимок на путь `DATABASE_PATH`. Старый WAL не должен оказаться рядом с восстановленной базой.
5. Запустите один экземпляр бота и проверьте каталог, административный вход и журналы запуска.

## Снаряжение и рецепты в админке

Откройте `/kombat` → «Управление снаряжением» → «Добавить снаряжение» или выберите существующий предмет. Один редактор связывает профиль, расходуемые материалы, изучение и источники дропа. Недостающий материал можно создать прямо в редакторе. Для нового свитка достаточно включить изучение: ресурс «Рецепт (название предмета)» создаётся автоматически при окончательном сохранении. Существующий свиток можно выбрать поиском.

Свиток изучается один раз и не входит в расход на изготовление. У готового предмета и свитка могут быть разные источники. «Кто изучил рецепт» относится к формуле изготовления; наличие этой функции определяется связью изучения, а не редкостью снаряжения.

Изменения снаряжения сохраняются в личном черновике. «Проверить и сохранить» показывает полный состав и источники; окончательное сохранение записывает связанные сущности одной транзакцией. Кнопка «Продолжить черновик» в админке позволяет вернуться после закрытия или перезапуска бота. Отмена черновика не изменяет опубликованный каталог. Одновременное редактирование одного предмета проверяется перед сохранением: чужие изменения не перезаписываются молча.

Для алхимии остаётся отдельный редактор результата и материалов с поиском, количеством результата и местом изготовления. Пустая формула не публикуется во время заполнения. Место крафта задаётся в рецепте и сохраняется при переименовании ресурса.

Используемый материал нельзя удалить, пока остаются зависимости. Админка показывает причину до подтверждения; база дополнительно защищает связи. Старые кнопки и ответы на прежние приглашения не могут изменить другой открытый объект.

## Дроп в карточке предмета

При добавлении ресурса или карты после примечания открывается меню «С кого падает». Отметьте одного или нескольких мобов и нажмите «Создать ресурс» или «Создать карту». Поиск работает по имени моба и названию локации; выбранные источники сохраняются при поиске и переходах между страницами. Кнопка «Показать выбранных» позволяет проверить список. Если предмет не падает с мобов или источник пока неизвестен, оставьте выбор пустым.

Предмет и его дроп записываются одной транзакцией после подтверждения. До этого можно вернуться к примечанию или отменить создание. У существующего ресурса или карты откройте «С кого падает» в меню редактирования: отметьте нужных мобов, снимите лишние отметки и сохраните источники. Возврат без сохранения отменяет только текущий выбор. Если другой администратор успел изменить дроп, сохранение предложит открыть актуальный список.

В редакторе снаряжения то же меню доступно отдельно для готового предмета и изучаемого свитка. Их источники включаются в общий черновик и сохраняются вместе с предметом. Добавлять дроп через меню моба по-прежнему можно. Эта доработка использует существующую таблицу дропа и не требует изменения схемы базы.

## Изменения схемы

`Database.connect()` проверяет `PRAGMA user_version`. Перед первым запуском новой версии приложения сделайте backup предыдущей базы. Текущая версия схемы — **3**. Миграция выполняется атомарно:

- Старые записи изучивших рецепт сохраняются как ручные записи; Telegram user ID не угадывается по имени. Повторы username устраняются без учёта регистра ASCII.
- Свитки типа `scroll_recipe` переносятся из ингредиентов в `recipe_learning_requirements`. Идентификаторы ресурсов, рецептов, источники дропа и записи игроков сохраняются. Неоднозначные связи останавливают миграцию с rollback.
- Добавляются черновики с проверкой версии, перенаправления объединённых ID снаряжения и явное место изготовления рецепта. Для старых алхимических рецептов переносится прежнее отображаемое место.
- Удаление используемого материала ограничено внешним ключом; самоингредиенты, циклы и неположительные количества отклоняются доменным слоем.
- Версия 3 добавляет явные связи родительских локаций и код специального ресурса, журнал изменений каталога, сохранённые FSM-сессии, ревизию каталога и результаты команд для безопасного повторного сохранения. Старые идентификаторы и строки каталога сохраняются.
- Известные старые числовые ID используются только миграцией с проверкой ожидаемых имён; пользовательские интерфейсы читают связи и код ресурса из базы.

Ошибка миграции вызывает rollback и закрытие соединения; неизвестная более новая версия схемы отклоняется. Изменение схемы не запускает автоматическое удаление совпадающих названий: объединение дублей — отдельная проверяемая операция. Разные уровни и другие характеристики могут означать разные предметы.

Файл снимка и код приложения должны соответствовать друг другу. Не понижайте `user_version` вручную. Для возврата на старую версию кода восстановите совместимый снимок после остановки процесса.

## Архитектура и гарантии сохранения

`bot.py` — точка запуска, `app.py` собирает отдельный Dispatcher, базу и сервисы для каждого экземпляра приложения. Публичные обработчики получают `PublicContext` с явными зависимостями. Фабрика административного роутера получает отдельный `RuntimeScope`; его база и права привязываются только на время текущего административного события, а вызов вне scope завершается ошибкой. Глобальных экземпляров базы и роутеров нет.

`Database` остаётся типизированным фасадом. Инфраструктура SQLite и миграции находятся в `storage/`, предметные операции вынесены в репозитории. Все репозитории используют общий контекст транзакции. Домен проверяет входные данные независимо от Telegram: допустимые типы, слоты, количества, связи рецепта и изучения. В обработчиках нет произвольных SQL-команд.

Многошаговые формы сохраняются в SQLite: после перезапуска можно продолжить ввод или нажать последнюю актуальную кнопку. `/kombat` явно начинает работу заново; черновики снаряжения доступны отдельно через «Продолжить черновик». Завершённая запись и переход FSM фиксируются атомарно там, где изменение зависит от шага ввода. Создание имеет стабильный идентификатор операции: повтор сохранения после сбоя возвращает прежний объект. Клавиатура доставляется после транзакции. Публикация следующего экрана связывает его кнопки, данные и состояние формы атомарно. Если новый текстовый шаг показан неоднозначно или его состояние не удалось сохранить, ответ без привязки к подтверждённому приглашению отклоняется; форму можно открыть заново через `/kombat`.

Незавершённый диалог истекает через `FSM_TTL_DAYS` без обновлений; технические истёкшие сессии удаляются небольшими порциями. Активные и ожидающие события используют одну блокировку на контекст, которая освобождается после последнего участника. При остановке сначала завершаются принятые обновления. Затем завершается фоновая аналитика; SQLite и HTTP-сессия закрываются после завершения работы с FSM и фоновых задач.

`catalog_changes` содержит автора, идентификатор операции и значения до/после правки. Журнал пишется в той же транзакции, что каталог, и не заменяет резервную копию. Для записи в каталог используйте API приложения: SQLite-триггеры журнала используют функции контекста, зарегистрированные подключением `Database`. Обычное read-only подключение остаётся пригодным для проверки и резервного копирования.

Inline-поиск ранжирует совпадения до ограничения страницы и загружает связанные карточки пакетно. Кеш ограничен размером, временем и количеством страниц; ревизия каталога меняется вместе с правками и делает устаревшие страницы недействительными. Статистика агрегирует события только для пользователей запрошенной страницы. `database.metrics` предоставляет число SQL-запросов, суммарное и максимальное время выполнения для диагностики.

История аналитики и завершённых черновиков автоматически не удаляется. Предварительный расчёт очистки работает строго в read-only режиме и не запускает миграции:

```sh
python -m maintenance --database game.db --draft-days 90 --analytics-days 365
```

Эта команда выводит только количество старых записей. Применение удаления истории — отдельная операция после проверки нужного срока хранения и резервной копии.

## Проверки разработки

```sh
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
python -m ruff check .
python -m ruff format --check .
python -m mypy
```

Тесты используют временные или in-memory базы и подменяют Telegram API; рабочий токен и рабочая база не нужны. Покрываются транзакции, парсеры, обработчики, приватность статистики, Unicode emoji и завершение задач, в том числе ожидающих блокировку FSM. Для проверки реального Telegram-поведения используйте отдельного тестового бота и копию базы.

GitHub Actions запускает эти проверки на Python 3.12 в Linux и Windows. Ruff проверяет исходный код и тесты; строгий mypy проверяет все модули приложения, включая обработчики Telegram и административные сценарии. Сырые строки SQL и данные FSM проверяются на границах; карточки, навигация и конфигурации редакторов используют явные типовые контракты.

## Данные и доступ

Статистика сохраняет Telegram ID, имя/username, время активности и текст поисковых запросов. Просмотр доступен администраторам в личном чате; механизм автоматического удаления старой истории пока не настроен. Учитывайте это при выборе срока хранения, выдаче доступа к файлам базы и резервному копированию.

Пользовательские токены задаются только через окружение. `.env`, SQLite-файлы, их WAL/SHM и локальные резервные копии исключены из Git. Журналы выводятся в стандартный поток; ротацию и перезапуск настройте средствами среды размещения.
